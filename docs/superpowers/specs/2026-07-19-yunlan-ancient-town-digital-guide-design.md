# 云岚古镇 AI 数字导游设计规格

## 1. 项目目标

本项目第一版要实现一个文旅导览场景下的 3D AI 数字人应用。用户进入虚拟示例景区“云岚古镇”后，可以通过文字向数字导游提问，例如“帮我规划一条半日游路线”。系统基于云岚古镇资料生成回答，展示聊天文本和路线步骤卡片，并由右侧 3D 数字人朗读回答、做简单嘴部动画。

第一版选择虚拟古镇，而不直接绑定真实景区。景区内容必须以可替换配置组织，后续切换到真实景区时，应主要替换景区 JSON 资料和提示词内容，不重写前端数字人、聊天、路线展示和后端 LLM 接入能力。

## 2. 已确认产品方向

- 行业方向：文旅导览。
- 场景类型：景区智能导游。
- 示例景区：虚拟古镇/古城，暂定名“云岚古镇”。
- 用户体验主线：像真人导游一样陪游客边走边问答。
- 数字人人设：年轻旅伴为主，带专业导游能力。
- 数字人外观：半现代半古风，现代年轻导游加少量古镇文化元素。
- 核心体验：综合陪伴型，包含故事讲解、路线推荐、服务问答。
- 第一条重点演示问题：“帮我规划一条半日游路线。”

## 3. 第一版 MVP 范围

第一版要完成以下功能：

- React 19 + Vite + TypeScript 前端项目。
- Koa 后端项目。
- ESLint、Prettier、Husky 工程规范。
- 左侧导览信息面板，右侧 3D 数字人布局。
- 快捷问题和自由输入同时支持。
- Koa 后端读取云岚古镇 JSON 资料。
- 后端通过 OpenAI-compatible 接口调用 LLM。
- LLM 回答限制在云岚古镇资料范围内。
- 路线类问题返回结构化路线卡片数据。
- 前端展示聊天记录和路线步骤卡片。
- 前端使用浏览器 Web Speech API 朗读回答。
- 朗读期间 3D 数字人做简单嘴部动画。
- README 和后端接口文档。

第一版不做以下功能：

- 浏览器录音和 ASR 语音识别。
- 后端真实 TTS 音频生成。
- WebSocket 流式下发文本、音频、viseme。
- 精准口型时间序列同步。
- 地图/路线图。
- 数据库、向量数据库或完整 RAG。
- 第三方数字人 Web SDK。
- 多景区后台管理。

## 4. 页面布局

采用左右分栏布局：

- 左侧为导览面板。
- 右侧为 3D 数字人展示区。

左侧导览面板包含：

- 景区标题和简短状态。
- 快捷问题按钮。
- 聊天记录区域。
- 用户输入框。
- 路线步骤卡片区域。

右侧数字人区域包含：

- Three.js 3D 人物模型。
- 古镇氛围背景或简化场景。
- 待机动画。
- 回答朗读时的简单嘴部动画。
- 可选的说话状态提示。

## 5. 数据内容规模

云岚古镇第一版内容规模为：

- 5 个景点。
- 2 条路线。
- 5 个服务点。
- 若干基础 FAQ。

建议初始内容：

景点：

- 南门牌坊。
- 云岚古桥。
- 茶坊小巷。
- 河畔灯巷。
- 听雨戏台。

路线：

- 半日经典路线。
- 亲子轻松路线。

服务点：

- 游客中心。
- 南门停车场。
- 公共厕所。
- 小吃街。
- 医务点/服务站。

## 7. 后端设计

后端使用 Koa。第一版提供 REST 接口，不使用 WebSocket。

核心模块：

- `scenic-data`：读取和校验云岚古镇 JSON 资料。
- `llm-client`：封装 OpenAI-compatible 调用。
- `guide-service`：组织系统提示词、景区资料和用户问题。
- `route-normalizer`：将路线类回答转换或补充为前端可展示的路线卡片。
- `api-docs`：提供接口文档。

LLM 配置通过环境变量读取：

```text
LLM_BASE_URL
LLM_API_KEY
LLM_MODEL
```

后端需要限制模型行为：

- 只回答云岚古镇相关问题。
- 不确定时说明“当前资料里没有明确记录”。
- 路线推荐必须优先使用 JSON 中已有路线。
- 不编造门票、开放时间、紧急服务等关键事实。

## 8. API 设计

### `GET /api/scenic-area`

返回景区基础资料、景点列表、路线摘要和服务点摘要。

用途：

- 前端初始化页面。
- 展示快捷问题和基础导览信息。

### `POST /api/guide/chat`

请求：

```json
{
  "message": "帮我规划一条半日游路线",
  "conversationId": "optional-session-id"
}
```

响应：

```json
{
  "answer": "推荐你从南门牌坊开始，依次游览云岚古桥、茶坊小巷、河畔灯巷，最后到听雨戏台休息。整条路线约 3 小时。",
  "cards": [
    {
      "type": "route-step",
      "title": "南门牌坊",
      "duration": "20 分钟",
      "description": "从这里了解云岚古镇的入口故事。"
    }
  ],
  "source": "llm"
}
```

错误响应需要包含明确错误码和用户可读提示。

## 9. 前端设计

前端使用 React 19、Vite、TypeScript。

核心模块：

- `AppShell`：页面整体布局。
- `GuidePanel`：左侧导览面板。
- `QuickQuestions`：快捷问题。
- `ChatMessages`：聊天记录。
- `RouteCards`：路线步骤卡片。
- `QuestionInput`：自由输入。
- `DigitalHumanStage`：右侧 Three.js 数字人舞台。
- `useSpeechSynthesis`：封装 Web Speech API。
- `useGuideChat`：封装请求状态、错误状态和聊天记录。

交互流程：

1. 页面加载，获取景区资料。
2. 用户点击快捷问题或输入自由问题。
3. 前端调用 `POST /api/guide/chat`。
4. 返回后追加聊天记录。
5. 如果响应包含路线卡片，更新卡片区域。
6. 使用 Web Speech API 朗读回答文本。
7. 朗读开始时通知 `DigitalHumanStage` 进入 speaking 状态。
8. 朗读结束后恢复 idle 状态。

## 10. 3D 数字人设计

第一版使用现成开源或免费 3D 人物模型，通过 Three.js 加载展示。

模型要求：

- 可以在浏览器中稳定加载。
- 文件体积适合演示。
- 最好支持基础头部或嘴部控制；如果模型不支持，第一版使用简化嘴部动画或替代表现。

动画要求：

- idle 待机动画。
- speaking 说话状态。
- 简单嘴部开合或表情变化。

第一版不追求精准口型同步。嘴部动画只需要和朗读状态大致同步，后续升级真实 TTS 与 viseme 时再做精细控制。

## 11. 错误处理

前端：

- LLM 请求失败时，聊天区显示友好错误。
- Web Speech API 不可用时，只展示文本，不阻塞主流程。
- 3D 模型加载失败时，显示占位数字人区域和错误提示。
- 提交问题时禁用重复提交。

后端：

- 缺少 LLM 配置时返回明确配置错误。
- LLM 超时或失败时返回稳定错误结构。
- 用户问题为空时返回参数错误。
- 景区 JSON 读取失败时启动失败或返回服务不可用。

## 13. 验收标准

第一版完成后应满足：

- 页面可以打开并展示云岚古镇 AI 数字导游。
- 页面左侧显示快捷问题、聊天区、输入框和路线卡片区域。
- 页面右侧显示 3D 数字人。
- 用户点击“帮我规划一条半日游路线”后，后端调用 LLM 返回回答。
- 回答内容基于云岚古镇 JSON 资料。
- 页面展示回答文本。
- 页面展示路线步骤卡片。
- 浏览器朗读回答文本。
- 朗读期间数字人进入 speaking 状态并做简单嘴部动画。
- 自由输入问题可用，但回答范围限制在云岚古镇。
- Lint、类型检查和构建命令可运行。
- README 和接口文档说明清楚。

## 14. 后续升级方向

后续可以按顺序升级：

1. 将虚拟云岚古镇资料替换为真实景区资料。
2. 接入真实后端 TTS，返回音频文件或音频流。
3. 增加 ASR 语音输入。
4. 增加 WebSocket 流式返回文本、音频和口型数据。
5. 增加 viseme 精准口型同步。
6. 增加地图或路线图。
7. 增加多景区配置和后台管理。
8. 增加 Coze 工作流或 RAG 知识库。

## 15. 主要风险

- 3D 模型不一定支持嘴部控制，需要预留占位动画方案。
- Web Speech API 的音色和浏览器兼容性有限，但适合第一版。
- LLM 可能编造景区信息，需要通过提示词和资料约束降低风险。
- 路线卡片最好由后端结构化返回，不应完全依赖前端从自然语言里解析。
- 第一版不要引入 ASR、WebSocket、viseme、地图，否则范围会明显扩大。
