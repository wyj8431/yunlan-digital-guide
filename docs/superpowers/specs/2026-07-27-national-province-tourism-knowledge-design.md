# 全国省级旅游知识库设计

## 目标

为数字导游补充覆盖全国 34 个省级行政区（含香港、澳门、台湾）的结构化旅游知识。每个省级行政区收录 12-20 个代表景点或目的地，总量约 500 个地点。用户询问省份、城市或具体景点时，回答必须提供可识别的地点名称和可执行路线，不能只输出通用旅行模板。

## 成功标准

- 34 个省级行政区均有独立知识记录。
- 每个省级行政区包含 12-20 个景点，景点记录包含名称、所在城市、类型和推荐理由。
- 每个省级行政区包含适合首次到访者的省内路线、交通衔接、住宿落点、季节提示和注意事项。
- 询问“山西有什么好玩的”时，检索结果明确包含平遥古城、云冈石窟、五台山、晋祠和壶口瀑布等具体地点。
- 询问具体景点时，检索优先返回该景点所属省份及景点详情。
- 省份推荐回答至少列出 6 个具体景点及所在城市，不再生成只有“上午核心景区、下午拍照”的空泛内容。

## 数据模型

新增独立的省级旅游数据模块，避免继续扩大现有单景点攻略文件。

```ts
type ProvinceTourismRecord = {
  province: string;
  aliases: string[];
  summary: string;
  highlights: Array<{
    name: string;
    city: string;
    categories: string[];
    recommendation: string;
  }>;
  routes: string[];
  transport: string;
  stay: string;
  season: string;
  tips: string;
};
```

`aliases` 覆盖自治区、特别行政区简称及常见口语名称。`highlights` 同时承担省份推荐和具体景点检索，不保存易快速变化的票价与营业时间。

## 模块边界

### 省级数据模块

只负责静态事实和推荐数据，不包含检索打分、模型提示词或接口逻辑。按区域拆分数据常量，最终导出统一的 `provinceTourismRecords`，保持单文件规模可读。

### 检索模块

将每个省份生成一条省级概览文档，并为每个景点生成一条景点文档：

- 省份名称或别名命中时，省级概览获得最高优先级。
- 景点名称命中时，景点文档获得最高优先级，同时保留所属省份概览作为补充。
- “全国推荐”等无具体省份的问题按区域返回代表性省份文档，避免任意按字符串排序截断。
- 现有乌镇本地资料和已有国内外单景点详细攻略继续保留，不改变其优先级和来源标记。

### 回答生成

检索上下文增加明确规则：省份推荐必须列出城市、具体景点和推荐理由，并给出一条跨城市路线。模型可以基于通用知识补充，但不得用通用模板替代已检索到的景点数据。

### 接口

保留现有 `/api/destinations` 行为，并增加省份目录输出，使前端或后续页面可以按省份读取景点列表。聊天接口继续通过现有检索链路自动使用新知识，不增加用户操作步骤。

## 数据质量约束

- 景点名称在同一省份内不能重复。
- 每省景点数必须在 12-20 范围内。
- 城市、分类和推荐理由不能为空。
- 景点与省份归属必须明确；跨省景观按主要管理或常用旅游入口归入一条记录，避免重复命中。
- 台湾、香港和澳门使用旅游信息表述，不引入政治性说明。
- 票价、开放时间、预约政策等动态信息统一提示以官方当天公告为准。

## 测试策略

1. 数据完整性测试：验证 34 个省级行政区、每省 12-20 个景点、字段完整和名称不重复。
2. 检索测试：覆盖山西、广东、新疆、西藏、香港、澳门、台湾，以及景点级精确查询。
3. 回答链路测试：验证省份问题注入具体景点上下文，模型提示词包含“至少 6 个具体景点”。
4. API 测试：验证省份目录和单省详情可读取。
5. 回归测试：运行现有导游、附件、图片、语音、前端和构建测试，保证新数据不会影响原有功能。

## 非目标

- 不接入收费或需要密钥的第三方旅游 API。
- 不提供实时票价、实时客流、酒店库存或天气。
- 本阶段不新增全国地图页面；数据和接口会为后续地图或省份筛选页面预留使用方式。
